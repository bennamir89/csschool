SESSION 1 EXPLAIN

The Design Brief

A concise statement that defines the problem, the client, and the desired outcome.

Key Components

P

Problem Statement

What needs to be solved? Be specific.

C

Client / Target User

Who is this for? Age, needs, context.

O

Outcome / Deliverable

What will be produced? A prototype? Full product?

S

Scope & Constraints

Budget, timeline, materials, limitations.

Example Design Brief

Problem: Elderly residents in care homes struggle to remember when to take their medication, leading to missed doses.

Client: Sunrise Care Home — 45 residents aged 70-95, many with mild cognitive impairment.

Deliverable: A simple, affordable medication reminder device that is intuitive for non-technical users.

Scope: Budget under $30/unit, must be operable without a smartphone, battery life ≥ 7 days.

SESSION 1 EXPLAIN

Specifications

Not all specifications are created equal. Engineers distinguish between two critical types:

Design Specifications

What it looks like and is made of

  • Dimensions: 15cm × 10cm × 5cm
  • Material: ABS plastic casing
  • Color: White with blue accents
  • Weight: ≤ 200g
  • Interface: 3 physical buttons

Performance Specifications

What it must do and how well

  • Alarm volume: ≥ 80dB at 1m
  • Battery life: ≥ 168 hours
  • Response time: < 0.5s button-to-alarm
  • Must store ≥ 30 alarm schedules
  • Drop test: survives 1.5m onto concrete

CS Connection

Think of design specs as the UI/UX requirements (layout, colors, font sizes) and performance specs as non-functional requirements (response time < 200ms, 99.9% uptime, supports 1000 concurrent users).

SESSION 1 EXPLAIN

Writing Measurable Specs

Vague specifications lead to vague products. Always use the MOST test.

MOST

The MOST Test

Every specification should pass all four checks

M

Measurable

Can you quantify it?

O

Observable

Can you test it?

S

Specific

Is it clear & precise?

T

Testable

Can you verify it?

Examples: Vague vs. Measurable

✗ Vague

"The device should be small and lightweight."

✓ Measurable

"The device must fit in a palm (≤ 12cm × 8cm) and weigh ≤ 150g."

✗ Vague

"The app should be fast."

✓ Measurable

"Screen load time must be < 2 seconds on 4G connection."

✗ Vague

"It should be easy to use."

✓ Measurable

"A first-time user must complete setup in ≤ 3 minutes without instructions."

SESSION 2 EXPLAIN

Gantt Charts

A visual timeline tool that shows tasks, durations, and dependencies in a project plan.

Anatomy of a Gantt Chart

Task
Wk 1Wk 2Wk 3Wk 4Wk 5Wk 6
Research & Analysis
Design Brief
Concept Sketches
Prototyping
Testing & Evaluation
Final Documentation
Core task
Documentation
Making/Building
Dependency flow

✓ Gantt Charts Show

  • • Task durations and start/end dates
  • • Overlapping tasks (parallel work)
  • • Dependencies (what must finish first)
  • • Milestones (key checkpoints)
  • • Critical path at a glance

✗ Gantt Charts Don't Show

  • • Resource allocation (who does what)
  • • Budget information
  • • Task complexity or difficulty
  • • Quality metrics
  • • Real-time progress (static tool)
SESSION 2 EXPLAIN

Risk Assessment

Every plan has uncertainties. Engineers systematically identify, evaluate, and mitigate risks.

Risk = Likelihood × Impact

Risk Likelihood Impact Risk Level Mitigation
Sensor component unavailable Medium High HIGH Identify 2 alternative suppliers early; order 2 weeks ahead
Team member absent Medium Medium MEDIUM Cross-train members; document all work in shared drive
Prototype fails safety test Low High MEDIUM Build safety testing into Week 3; have backup design ready
Budget overrun Low Medium LOW Add 15% contingency to budget; track spending weekly

CS Connection

In software, risks include: scope creep, API changes, security vulnerabilities, data loss. Agile mitigates these through sprints, user stories, CI/CD, and retrospectives. Ask students: "How does a risk assessment table compare to a sprint retrospective?"

SESSION 2 EXPLAIN

Milestones & Critical Path

Two more essential planning concepts that keep projects on track.

Milestones

Key checkpoints that mark the completion of a major phase. They have zero duration — they're moments in time.

M1: Design Brief Approved
M2: Concept Design Finalized
M3: Working Prototype Complete
M4: Testing Passed & Sign-off

CS analogy: A git tag or release version (v1.0, v2.0)

Critical Path

The longest sequence of dependent tasks. If any task on the critical path is delayed, the entire project is delayed.

Example

Research (2 wk) → Design (1 wk) → Prototype (2 wk) → Test (1 wk)

Critical Path = 6 weeks

Documentation (parallel) doesn't affect the path

CS analogy: The critical path is like a synchronous function call chain — if one blocks, everything blocks. Non-critical tasks are like async operations.

Task 1: Design Brief (6 marks)

  • Clear problem statement (2 marks) — identifies the specific need
  • Client identified with context (1 mark)
  • Deliverable clearly described (1 mark)
  • Scope/constraints included (budget, timeline, materials) (2 marks)

Task 2: Specifications (8 marks — 1 per spec)

  • 1 mark each for a correct, measurable spec with a valid test method
  • Half mark if spec is present but not fully measurable
  • Zero if vague ("should be secure") or wrong type (design spec in performance column)

Task 3: Gantt Chart (6 marks)

  • ≥ 8 tasks shown (2 marks)
  • Durations are realistic and proportional (2 marks)
  • At least 2 milestones marked (1 mark)
  • At least one dependency shown (task B starts after A) (1 mark)

Task 4: Risk Assessment (5 marks)

  • 3 relevant risks identified (1.5 marks — 0.5 each)
  • Likelihood and impact rated reasonably (1 mark)
  • Practical, specific mitigation strategies (2.5 marks — nearly 1 each)

Task 5: Critical Path (5 marks)

  • Correctly identifies the longest dependent chain (2 marks)
  • Explains WHY it's critical (1 mark)
  • Correctly describes the impact of a 1-week delay (2 marks)
